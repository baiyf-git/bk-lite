# BK-Lite 节点管理 · 2026 年 10 月迭代规划

Status: ready for scheduling  
Audience: 产品 / 研发排期 / 与 APM 共背  
Scope: 节点管理（`web/src/app/node-manager` + `server/apps/node_mgmt`）  
Horizon: 国庆后约 3 周、约 1 组全栈；可砍不加项

一句话价值：装完当场能信；点进节点，按应用看见这台机器上监控 / 日志 / CMDB / APM / 执行器各在不在跑。

本文是最终十月规划，可直接拆故事。拍板后主保收短：只做「装完能验」和「详情按应用分组」。

## 2. 证据分层

### 仓库事实

- 安装通道已在：`InstallerViewSet`（安装 / 卸载 / 重试 / 手动、采集器安装、下载、安装命令）。不是十月缺口。
- 心跳半套已在：Sidecar 回写 `Node.status` / `metrics` / `updated_at`；列表 60 秒内上报为活跃；采集器按心跳计数。见 `services/node.py`。
- 失败类型已在、人话没有：`FAILURE_SUMMARY_MAP` 能区分超时、连不上、鉴权、磁盘、架构、时钟偏差，文案是英文。见 `utils/installer_schema.py`。
- 节点列表托管列已经是「按状态汇总数量」（正常 N / 异常 M），用户确认保持现状，**不要**加应用列。
- 节点详情左侧组件列表**按运行状态分组**，不按应用。见 `collectorDetail/index.tsx` 的 `getSortedGroupedCollectors`。
- 现网 `CollectorConstants.TAG_ENUM` 应用标签：`monitor` / `log` / `cmdb` / `apm` / `executor`。预置标签：Telegraf → `monitor` + `cmdb`；Vector / Filebeat → `log`；OTel-Collector → `apm`；Ansible / NATS-Executor → `executor`。
- `ALLOWED_PUSH_TARGETS = ("cmdb", "monitor")`。`Node` 只有 `cmdb_id` / `monitor_id`。Log、APM **没有** `ingest_from_source` 一类主机接收面。Log 的 `CollectInstance.node_id` 是建日志采集实例时绑的节点，不是「把主机推进 Log」。
- 可升级筛选已有；批量升级任务没有。十月不做升级。
- APM 接入页已能给出区内 OTLP/HTTP `:4318` 和五类语言系统内下载。见 `docs/operations/apm-probe-artifact-release.md`。

### 已确认产品决定（本次拍板）

- 十月主保只有第 1、2 条。
- 列表不加 Monitor / Log / APM 列；优化只放在详情组件列表，按 app 标签分组。
- 「某应用正常」= 该应用标签下组件出现在心跳里并且在跑；与第 1 条同一口径。
- 批量升级十月不做；以后优先控制器，采集器另迭代。
- 不扩 `push_targets` 到 log / apm，不写「推主机到 log/apm」。
- APM 接入下载以 APM 页为主；节点管理不重做接入页。

### 当前假设

- 一个采集器可出现在多个应用组（Telegraf 同时在 monitor 与 cmdb）。这是标签事实，不要拆成两份进程。
- 详情只展示这台节点上已有的托管组件；没有某标签组件时，该组为空或不出现，不在详情里发明「缺失矩阵」。
- 第 1 条人话覆盖「安装失败」和「任务成功但没在跑」。

### 待确认（不挡排期）

- 详情空组：完全隐藏，还是显示「该应用暂无组件」。默认隐藏空组，避免五个空壳。
- 组头「未在跑」是否单独于「异常」：心跳里没有该组件算未在跑；心跳里有但状态非运行算异常。与第 1 条对齐即可。

## 5. 需求拆解

### 5.1 装完能验

**背景**  
安装任务能走到成功或失败，列表也能标 Sidecar 是否活跃。现场仍会问：采集器在不在跑？刚才为什么失败？任务成功但采集没上报，不能当成已经好了。

**用户与场景**

- 交付刚装完一批节点，要在安装结束页或节点详情确认：最近心跳时间、该装的采集器在跑，才能交给三域配策略。
- 失败时要立刻看懂：连不上、权限不够、磁盘不够、包不对、时钟差太多，还是装上了没回连；下一步是重试、改凭据、查云区域，还是改手动。
- 值班看到「安装成功」但不出数，要能核对心跳和采集器，而不是先怀疑策略。

**范围**

- 做：安装结束（含手动回连）和详情展示最近心跳、控制器是否心跳、相关采集器是否在跑；高频失败用中文说明原因和下一步；任务成功但无心跳或采集器未出现在心跳里，不得标采集正常。
- 不做：重写安装状态机；任意命令诊断台；维护窗；重做安装通道。

**方案要点**  
复用 Sidecar 心跳、`Node.status.collectors`、`Installer` 任务结果、`FAILURE_SUMMARY_MAP`。在现有安装进度页和节点详情补：最近心跳、是否在跑、中文原因。活跃窗口继续 60 秒。不新做状态机。

**验收标准（可测）**

1. 自动或手动安装结束后，同一任务能读到最近心跳时间；无心跳不得显示采集正常。
2. 控制器回连成功、目标采集器未出现在心跳或状态非运行：页面为「未在跑」，不得因任务成功写成已覆盖。
3. 连不上、鉴权失败、超时、时钟偏差、包架构不匹配：页面是中文人话 + 下一步，不直接甩英文 `error_type`。
4. 同一失败任务可重试或转手动，节点保留。
5. 生产日志不含凭据、安装 Token、应答正文。

**优先级与可砍条件**  
P0，不可砍。人话可先覆盖上述 5 类；「未知」用「安装未完成，请看步骤或重试」。不可把「在跑 + 心跳」降成只改文案。

**依赖与共背方**  
只依赖现有安装和心跳。第 2 条复用同一「在跑」口径。不依赖告警中心。不依赖 Log/APM ingest。

### 5.2 详情按应用分组

**背景**  
交付要知道这台机器上监控、日志、APM 各有哪些组件、在不在跑。用户明确：**列表加应用列会很怪**，列表继续用「正常 N / 异常 M」。要看应用，点进详情再分。

**用户与场景**

- 打开某台节点详情，先看 Monitor 组：Telegraf 在跑；再看 Log 组：Vector / Filebeat 是否在跑；再看 APM 组：OTel-Collector 在不在。
- 组头一眼看到该应用正常 / 异常 / 未在跑各几个；点 Telegraf 仍进现有主配置 / 子配置。
- 列表验收时仍扫「正常 3 / 异常 1」，不在表格里找 Monitor 列。

**范围**

- 做：详情托管组件列表按采集器 **app 标签**分组，顺序建议 monitor → log → cmdb → apm → executor。组头展示该组汇总（正常 / 异常 / 未在跑）。点组件进入现有配置 / 子配置。Telegraf 同时出现在 monitor 与 cmdb（一份组件，两个组能找到）。「某应用正常」= 该标签下组件在心跳里且在跑。
- 不做：列表增加应用列；云区域覆盖大盘；主机 × 模块矩阵；按 CMDB 自动铺采集器；改列表现有汇总。

**方案要点**  
用现成 `TAG_ENUM` 的 `is_app` 标签和采集器 `tags`，改详情左侧列表的分组键：从按 `status` 改为按 app 标签。在跑口径与第 1 条相同。配置抽屉不换入口。

**验收标准（可测）**

1. 节点列表托管列仍是按状态汇总（正常 N / 异常 M），没有 Monitor / Log / APM 列。
2. 详情能看到应用组。有 Telegraf 的节点：monitor 组与 cmdb 组都能找到 Telegraf。有 Vector / Filebeat：在 log 组。有 OTel-Collector：在 apm 组。有 Ansible / NATS-Executor：在 executor 组。
3. 组头数字与组内组件一致；该组组件都在心跳且在跑时，组头可称为该应用正常。
4. 组件在详情标「在跑」，但最近心跳已超时：不得算该应用正常（与第 1 条同一口径）。
5. 点组内组件，仍打开现有配置 / 子配置，不新开第三套向导。
6. 没有任何 app 标签的组件：单独「其他」或仍按原列表垫底，不得丢数据。

**优先级与可砍条件**  
P0，分组不可砍。可砍：空组展示、组内二次排序。不可改回「只按状态平铺」或「把应用列加回列表」。

**依赖与共背方**  
依赖第 1 条在跑 / 心跳口径。APM 共背：看这台机器 APM 采集在不在，以详情 APM 组的 OTel 为准；复制接入点和下载探针去 APM 接入页。Monitor / Log 不为此改策略页。

---

### 5.3 APM 接入（不进节点管理主保，写清操作）

节点管理十月**不**再单列「半日下探针」故事。现场操作分成两页，避免两套向导：

1. **节点详情 → APM 组**：确认 OTel-Collector 在、最近心跳在、状态在跑。这是第 2 条的一部分。
2. **APM 接入页**：选同一云区域，复制区内 OTLP（与页上展示一致，区内 `:4318`）；选语言，下载或复制系统内探针命令。结果由 APM 页区分：成功 / 该语言包未发布 / 区域未配。不做 K8s 注入。

节点管理若顺手在云区域或详情放「打开 APM 接入」链接，算体验，不算第三条主保，没有链接也不挡第 1、2 条验收。

## 7. 给群聊的短结论

十月节点管理收成 2 条。1）装完能验：心跳、采集器在不在跑、失败说中文；任务成功但没心跳 ≠ 采集正常。2）列表保持正常/异常汇总；点进详情按 monitor / log / cmdb / apm / executor 分组看组件。批量升级整月不做。不要推主机到 log/apm（对端没有这对象）。APM 接入点和探针下载仍走 APM 页；节点管理只保证详情 APM 组能看见 OTel 在不在跑。
