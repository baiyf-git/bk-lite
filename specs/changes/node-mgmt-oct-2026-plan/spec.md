# BK-Lite 节点管理十月迭代规划（PM 优化稿）

Status: proposed  
Audience: 产品 / 研发排期  
Scope: 仅 BK-Lite 节点管理（`web/src/app/node-manager` + `server/apps/node_mgmt`），以及与 Monitor / Log / APM 的身份接缝  
Horizon: 国庆后约 3 周，约 1 组全栈；略满可砍，不再加项

本文是可排期产品稿，不是实现规格。写法对齐 Monitor #20、APM #21、Log #22。  
三域十月继续主保策略侧（相对计算 + 配完能验）；**探针安装不进 Monitor / APM / Log 十月清单**，由节点管理承接「装得上、看得见、接得上」。

---

## 0. 证据分层

### 仓库事实

- 模块路由已齐：`node` / `cloud_region` / `sidecar_env` / `collector` / `controller` / `configuration` / `child_config` / `installer` / `package`，以及 sidecar 用的 `open_api`。见 `server/apps/node_mgmt/urls.py`。
- 核心对象：`Controller`、`Node`（含 `cloud_region`、`cmdb_id`、`monitor_id`、`push_status`、`install_method`）、`Collector`、`CollectorConfiguration`、`ChildConfig`、`Action`、`SidecarApiToken`。采集器动作任务 `CollectorActionTask` 只有 start / restart / stop。
- 节点上**没有** `log_id`、`apm_id`。跨模块推送白名单写死为 `ALLOWED_PUSH_TARGETS = ("cmdb", "monitor")`，前端类型同样只有这两项。现网推送只到 CMDB 和 Monitor。见 `services/module_push.py`、`web/src/app/node-manager/utils/modulePush.ts`。
- 安装通道已在：`InstallerViewSet` 提供控制器安装 / 卸载 / 重试 / 手动安装、采集器安装、Windows/Linux 安装包下载、安装命令。首次触达走 SSH、WinRM（云区域内 Executor）或 Token / 手动脚本，不是新做一套远程执行平台。
- 心跳与活跃：Sidecar 心跳回写 `Node.status` / `metrics` / `updated_at`。列表把「最近 60 秒有上报」标成活跃；采集器状态按心跳里的 collectors 聚合展示（运行中 / 异常计数）。见 `services/node.py`、节点列表页。
- 安装失败已有类型化摘要（超时、连不上、鉴权、磁盘、架构不匹配、时钟偏差等），文案目前是英文技术句，页面进度能看到步骤，但「装完后采集器 / 配置是否真在跑、最近心跳是何时、失败为什么」还没有人话闭环。见 `utils/installer_schema.py` 的 `FAILURE_SUMMARY_MAP`。
- 覆盖视图不存在：列表能看单台节点的 Sidecar 和托管采集器数量，不能一眼看「主机 × 采集器 × 模块（Monitor / Log / APM）」缺哪一块。采集器标签里已有 `monitor`、`apm`（如预置 `OTel-Collector`），Log 侧通过 `node_ids` 下配置，但节点侧没有三域覆盖汇总。
- 版本：`NodeComponentVersion.upgradeable` 和列表「可升级」筛选已有；`VersionUpgradeService` 只算最新版本。仓库里**没有**批量升级控制器 / 采集器的任务，也没有回滚摘要。
- 架构事实：Controller / Sidecar 托管本机采集器；主配置 + 子配置下发；云区域隔离。APM 接入点已按云区域解析区内 OTLP/HTTP `:4318`，探针制品走 `NODE_SERVER_URL` 的 APM 下载口，不走节点管理包上传。见 `docs/operations/apm-probe-artifact-release.md`、`server/apps/apm/services/integration_configuration.py`。
- 安装时勾选的 `push_targets` 只对已存在节点立即推；新装节点要等 Sidecar 首次注册后再消费延迟目标。延迟推送已有记忆，但不能表述成「装完就自动和三域对齐」。

### 已确认产品决定

- 十月主题：【节点管理：探针装得上、状态看得见、三域接得上】。
- 主保 1 + 2 + 3 + 4；第 5 条有余量再做，否则移十一月。
- 维护窗 / 静默 / 级别抑制归告警中心，节点管理不做。
- 探针安装不进 Monitor / APM / Log 十月清单；三域继续主保策略侧。
- 与三域共背：1 / 2 / 3 对 Monitor + Log；4 对 APM。
- `push_targets` 现网仅 cmdb / monitor，十月必须扩到 log、apm，并做节点 ↔ CMDB ↔ 三域实例 ID 对齐。
- 保持「底座（Controller / Sidecar）+ 插件（采集器）」双层；安装保留远程批量 + Token / 手动；心跳 + 状态是信任前提。
- 节点管理 ≠ 远程执行平台。云助手 / TAT / Ansible 只当首次触达通道，不当产品本身。
- 策略化分组、灰度回滚、K8s 语言探针注入后置。

### 当前假设

- 「覆盖」按已售模块裁剪：没买 Log 就不展示 Log 列；没买 APM 就不展示 APM 列。与现网推送目标按已售模块勾选同一套纪律。
- 第 3 条的 log / apm 推送，复用现有 `module_push` 的「用户显式勾选、失败不阻断纳管、详情可补推」，不新造第二条同步总线。
- APM 十月在节点管理侧的验收，是「半日能指到正确区内接入点、探针制品能下到机器」，不是把语言 Agent 装成长期托管采集器。
- 第 1 条的「说人话」覆盖安装失败和装完不在跑两类；不重写全部底层 error_type。

### 待确认（不挡排期）

- Log / APM 对端是否已有与 Monitor 同级的 ingest 接收面。节点侧十月先把目标、关联字段和补推入口开出来；对端契约由 Log / APM 共背，缺接收面时节点只记录「对端未就绪」，不假装推成功。
- 覆盖一览的默认入口：节点列表加列，还是云区域下一张覆盖页。十月只做一张表，不做第二套大盘。
- 语言探针下发是「给下载命令 / 包」还是「经 Sidecar 落到指定目录」。十月最低验收是目标机能拿到制品；经 Sidecar 落盘若 W2 仍重，降级为下载入口 + 校验哈希。

## 1. PM 审阅意见

### 1.1 十月要验证的价值

客户买的不是「又一个装 Agent 的页面」。他们要的是：机器纳管之后，监控 / 日志 / 调用链真的在采，坏了能看懂，不用再 SSH 猜。

现在的半闭环是：自动 / 手动安装已经能把控制器装上去，心跳和采集器计数也在列表里，CMDB / Monitor 也能勾选推送。缺的是后半段——

1. 装完不敢信：成功页过了，采集器或配置没跑，失败原因是英文技术句。
2. 规模一看就瞎：不知道这台机器 Monitor / Log / APM 各缺哪块采集器。
3. 身份对不齐：节点有 `cmdb_id` / `monitor_id`，没有 log / apm 关联；`push_targets` 还不认识这两域。
4. APM 接不上手：区内 OTLP 和多语言探针下载已经在 APM 侧生成，节点管理还没把「指到正确接入点、把探针下到机器」收成共背验收。

十月只补这四段。批量升级是加分项，不是主题。

### 1.2 优先级

| 优先级 | 条目 | 判断 |
|---|---|---|
| P0 主保 | 1 装完能验 | 没有「在跑 + 心跳 + 人话失败」，安装通道再完整也交不出去。现有心跳和失败类型是半成品，按补齐做，不重做安装。 |
| P0 主保 | 2 覆盖一览 | 售前和交付要一张表回答「这些机器监控 / 日志 / APM 谁没装」。没有它，第 1 条只对单机有用。 |
| P0 主保 | 3 `push_targets` 扩到 log、apm + 三 ID 对齐 | 代码级真缺口。现网只推 cmdb / monitor。三域十月策略再好，实例对不上节点就是两张皮。 |
| P0 主保 | 4 APM 接缝 | 与 APM 共背。节点管理不负责策略，负责区内接入点和探针能下到机器。半日能指到、能下载，才算十月节点管理成功。 |
| P1 可砍 | 5 批量升级 + 回滚摘要 | 可升级筛选已有。缺的是任务化升级和回滚摘要。有余量再做，否则整条移十一月。 |

节点管理主保：1 + 2 + 3 + 4。第 5 条可砍。  
三域十月总括仍是策略侧「相对计算 + 配完能验」；节点管理不抢那条主题，只把采集底座接到能用。

### 1.3 伪需求（不要当十月新功能）

1. **做成第二套 Ansible / Salt / TAT 远程执行平台。** SSH、WinRM、Token / 手动已经是首次触达。十月补的是验、覆盖、接缝，不是任意命令、剧本市场或作业平台。
2. **SkyWalking 类语言 Agent 的 K8s 注入。** APM 另有路径。十月节点管理只做区域 OTLP + 制品下发入口，不注入 sidecar、不改客户 Deployment。
3. **完整插件商店生态、动态 CMDB 拓扑策略引擎。** 策略化分组后置可薄做；商店、动态拓扑、按 CMDB 自动铺采集器不是 3 周主题。
4. **把抑制 / 维护窗做进节点管理。** 这是告警中心的运营能力。节点管理不判断「这段时间别响」。
5. **重做一套安装通道。** 自动 + 手动 + 安装令牌已在。再做第三套安装器只会和现网抢入口。应补「能验 / 覆盖 / 接缝」。

### 1.4 与 Monitor / APM / Log 及告警中心的边界

| 谁做 | 十月做什么 | 不做什么 |
|---|---|---|
| 节点管理 | 把控制器 / 采集器装上并验在跑；给出主机 × 采集器 × 模块覆盖；把节点推到 log / apm 并对齐实例 ID；帮 APM 指到区内 OTLP、把探针制品下到机器 | 不算 P95 / 环比；不配日志策略；不做调用链；不设维护窗 |
| Monitor | 策略相对计算 + 试跑（见 #20）。采集器是否在节点上、主机是否对齐，与节点管理共背第 1 / 2 / 3 条 | 不在监控策略页做探针安装 |
| Log | 策略相对计算 + 试算 + 样本回跳（见 #22）。日志采集器覆盖和实例 ID 与节点管理共背第 1 / 2 / 3 条 | 不在日志十月清单做探针安装 |
| APM | 策略相对计算 + Trace 隔离（见 #21）。区内接入点和探针下发与节点管理共背第 4 条 | 不在 APM 十月清单做 K8s 注入或重做安装器 |
| 告警中心 | 维护窗、静默、级别抑制、降噪、升级 | 不代替节点管理看心跳，不算覆盖 |

对外只说一句：**节点管理负责装得上、看得见、ID 对得上；三域负责各自怎么判定；告警中心负责响不响的运营。**

对比口径是「节点管理底座 + 三域判定 + 告警中心运营」，不是拿节点管理单品去对标蓝鲸作业平台或 Ansible Tower。

### 1.5 3 周可交付性

约 1 组全栈、国庆后 3 周。能做完的是「验状态 + 一张覆盖表 + 推送白名单扩两域 + APM 接缝」。批量升级另算。

| 工作包 | 为什么能进 3 周 | 为什么不能再加 |
|---|---|---|
| 装完能验 | 心跳、采集器状态、安装步骤、失败类型都已在；补人话摘要和「最近心跳 / 是否在跑」验收面 | 不重写安装状态机，不新造远程执行 |
| 覆盖一览 | 节点、托管采集器、采集器标签、三域实例关联已有原料；做汇总查询和一张表 | 不做拓扑图、不做自动补齐引擎 |
| `push_targets` + ID | 现成编排只是白名单少两项，字段和前端类型跟着扩；对端按 Monitor 契约共背 | 不重做 Outbox，不改 CMDB 身份规则 |
| APM 接缝 | 区内 OTLP 和探针下载地址 APM 已能解析；节点管理补「指到 / 下到」和共背验收 | 不做 K8s 注入、不做语言运行时托管 |
| 批量升级 | 筛选已有，任务模型可抄安装 / 动作任务 | 灰度、分批策略、自动回滚编排是另一条产品 |

略满点在：第 3 条要等 Log / APM 接收面、第 4 条要和 APM 对验收词。这已经够满。  
**结论：主保 1 + 2 + 3 + 4 可交付；5 默认有余量再排。不要再加项。**

## 4. 逐条说明

### 4.1 装完能验

**背景：** 安装任务能走到成功或失败，列表也能标 Sidecar 是否活跃。交付现场仍然会问两句：采集器到底在不在跑？刚才为什么失败？现在要么看英文步骤，要么自己 SSH。相对计算再好，采集没在跑也是空的。

**做什么：** 安装结束（含手动安装回连）后，同一条任务 / 同一台节点能看见：控制器是否心跳、最近心跳时间、该节点上本次相关的采集器和配置是否在跑。失败时用已有失败类型翻译成人话（连不上、权限不够、磁盘不够、包不对、时钟差太多、装上了但没回连），并给出下一步（重试 / 改凭据 / 检查云区域 / 改去手动）。不新开远程诊断 Shell。

**怎么实现：** 复用 Sidecar 心跳、`Node.status.collectors`、`Installer` 任务结果和 `FAILURE_SUMMARY_MAP`。在安装进度页和节点详情补「最近心跳 / 是否在跑 / 人话原因」，不要另做一套状态机。活跃判定继续用现网 60 秒窗口，文案写清「最近心跳」，不要只丢一个绿灯。

**验收：**

- 自动或手动装完，进度页能看到最近心跳时间和采集器 / 配置是否在跑；只写「任务成功」但采集器未上报，不得标成采集正常。
- 常见失败（连不上、鉴权、超时、时钟偏差、包架构不匹配）页面是人话，不直接甩英文 `error_type`。
- 失败可从同一条任务重试或转手动，不丢节点。
- 不出现新的「任意命令调试」入口。
- 生产日志仍不打印凭据、安装 Token、应答正文。

**非目标：** 重做安装器、作业平台、实时 SSH 控制台、告警中心维护窗。

**依赖：** 现有安装任务和心跳。与告警中心无关。与 Monitor / Log 共背「装完后本域采集器能被看见在跑」。

### 4.2 覆盖一览

**背景：** 交付要回答「这批机器监控齐了吗、日志齐了吗、APM 齐了吗」。现在只能一台一台点进托管程序。缺一台 Vector 或没装 OTel，要到出数失败才知道。

**做什么：** 在云区域节点语境下给一张覆盖表：行是主机（节点），列是模块（Monitor / Log / APM，按已售裁剪）和对应采集器。格子区分：已安装且在跑、已安装但未在跑 / 无心跳、未安装、不适用（该模块不需要这台机器）。能筛「某模块缺失」。点格子回到现有节点详情或安装入口，不新做第三套安装向导。

**怎么实现：** 汇总已有节点、托管采集器、采集器标签（`monitor` / log 类 Beat·Vector / `apm` 的 OTel）、以及三域已关联实例。查询放在 `node_mgmt` 服务层，列表或独立覆盖页二选一，十月只做一张。不要为了「好看」去画 CMDB 拓扑。

**验收：**

- 同一云区域、同一权限范围，能一眼列出：哪些主机缺 Monitor 采集器、哪些缺 Log、哪些缺 APM（OTel 或语言探针入口）。
- 已装但心跳超时的，不得显示成「已覆盖」。
- 未购买的模块不出现列，也不出现「缺失」误报。
- 覆盖数据与节点详情的托管程序一致，不能两个入口各算各的。

**非目标：** 自动按 CMDB 拓扑铺采集器、覆盖趋势大盘、跨云区域全球地图。

**依赖：** 第 1 条的「在跑 / 心跳」口径。与 Monitor / Log 共背缺失定义（例如主机监控看 Telegraf，文件日志看 Vector / Filebeat）。

### 4.3 `push_targets` 扩到 log、apm，并对齐实例 ID

**背景：** 节点已经能勾选推到 CMDB、Monitor，并回填 `cmdb_id` / `monitor_id`。Log 和 APM 的实例还对不上同一台机器。三域十月在各自策略里干活，拼数据时仍会认成三台主机。

**做什么：** 推送白名单增加 `log`、`apm`。创建 / 安装 / 详情补推与现网 cmdb / monitor 同一套交互：已售默认勾选，用户取消则不推，失败不阻断纳管。节点持久化对应关联 ID（与现网 `cmdb_id` / `monitor_id` 同级），`push_status` 按目标记录。完整勾选成功后，节点、CMDB、三域实例能互认同一台机器。冲突继续拒绝静默合并。

**怎么实现：** 扩 `ALLOWED_PUSH_TARGETS` 和前端 `ModulePushTarget`；`Node` 补 log / apm 关联字段；`module_push` / `module_link` / `module_ingest` 按 Monitor 既有契约加两个目标。对端没有接收面时，状态写成可补推的失败 / 未就绪，禁止写假成功。不级联暗建：只推用户勾选的目标。

**验收：**

- 安装或详情勾选 log / apm 后，白名单接受这两项目标；未勾选绝不推。
- 成功后节点能看到对应实例 ID，对端能看到 `node_id`；再补推幂等，不建重复实例。
- 只推 Monitor 时行为与现在一致；老节点没有 log / apm ID 时页面是「未推送」而不是报错。
- 现网仅 cmdb / monitor 的存量数据不回归。
- 对端未就绪时，节点仍在，状态可人话读懂，详情可再推。

**非目标：** 重做 CMDB 拉同步、跨模块公共总线、把 Log / APM 业务事实反推回节点。

**依赖：** Monitor 现有 ingest 契约作样板；Log / APM 共背接收与回填。身份规则继续以节点 ID 优先，CMDB 仍用 `inst_uuid`。

### 4.4 APM 接缝：区内 OTLP + 探针下发

**背景：** APM 接入页已经能按云区域给出区内 OTLP/HTTP 地址，也能拼出五类语言探针的系统内下载地址。现场卡在：指错区域、机器下不了包、节点管理不知道这台机器 APM 是否接得上。K8s 注入是另一条路，十月不做。

**做什么：** 在节点管理（及 APM 接入指引可跳转处）明确：这台机器 / 这个云区域的 OTLP 接入点是哪一个；Java / Python / Node.js / Go / .NET 探针从哪里下、如何校验下到了。与 APM 共背同一验收句：熟练交付半天内能指到正确接入点，并能把探针制品放到目标机器。OTel Collector 作为 APM 托管采集器，纳入第 2 条覆盖，不另做第四个安装产品。

**怎么实现：** 复用云区域 `proxy_address` / `NODE_SERVER_URL`、预置 `OTel-Collector`、APM `open_api/probe/download`。节点管理提供「接入点 + 下载 / 下发」入口和结果（成功 / 下不到 / 区域未配）。不要把 APM 探针登记成普通长期采集器进程，除非它本来就是 OTel Collector。禁止为了方便去访问 GitHub / PyPI。

**验收：**

- 选对云区域后，给出的 OTLP 地址与 APM 接入页一致，都是区内 `:4318`，不是公网 Token 入口。
- 五类语言（当前平台已声明的范围）能从系统内地址下载；缺制品时说「该语言包未发布」，不装成网络故障。
- 目标机拿到的文件能对上平台登记的制品（至少校验大小或哈希）；下发失败可重试。
- 与 APM 共背：半日路径走得通（选区域 → 看到接入点 → 下载探针 → 机器上有文件）。
- 不出现 K8s webhook / 自动注入开关。

**非目标：** SkyWalking 风格注入、RUM、公网 OTLP Token、把 `deploy/apm` 当生产真相源、语言运行时生命周期托管。

**依赖：** APM 接入配置与探针制品发布（`docs/operations/apm-probe-artifact-release.md`）。第 2 条覆盖把 OTel 算进 APM 列。告警中心无关。

### 4.5 批量升级控制器 / 采集器（可砍）

**背景：** 列表已经能筛「可升级」，版本旁也有升级提示。真要升一批，还是靠重新走安装，没有任务摘要，更没有回滚摘要。这是成熟度，不是十月信任闭环。

**做什么（仅有余量）：** 对已标可升级的控制器 / 采集器发一条升级任务，复用安装任务的节点级进度。结束后给成功 / 失败数，以及「回到升级前版本」的回滚摘要（能看清谁回得去、谁要手工处理）。不做灰度百分比、不做维护窗编排。

**怎么实现：** 复用 `NodeComponentVersion`、`PackageVersion`、安装 / 动作任务模型。不要新写作业引擎。回滚只针对本次任务写过的节点。

**验收（只有真做时才算）：**

- 可升级筛选结果能直接进入升级任务，操作系统 / 架构不一致的批次拒绝提交。
- 任务能看到每台成功、失败、人话原因。
- 回滚摘要能列出可回滚节点和升级前版本；回滚失败不删节点。
- 未标可升级的节点不能被混进任务。

**非目标：** 灰度策略、分批日历、与告警中心维护窗联动、跨云区域一键全球升级。

**依赖：** 第 1 条人话失败。与三域策略无关。

**砍法：** 默认 W3 才看；1～4 任一未验收则整条移十一月，不做到「只加个升级按钮」。

## 5. 建议排期（3 周，1 组全栈）

| 周次 | 交付 | 砍闸 |
|---|---|---|
| W1 | 第 1 条：心跳 / 在跑进入安装结束态；人话失败上进度页。第 3 条：白名单 + 字段扩 log / apm，先打通与现网相同的补推形态 | 不动升级；不对端未就绪就写成功 |
| W2 | 第 2 条覆盖表；第 3 条与 Monitor / Log 对 ID；第 4 条接入点展示 + 探针下载入口 | 覆盖只做一张表；探针落盘若重，先保下载 + 校验 |
| W3 | 第 1～4 条打磨与共背验收；半日 APM 路径走通；有余量再开工第 5 条 | 第 5 条未开工就移十一月 |

并行约束：第 2 条依赖第 1 条的在跑口径；第 4 条可与第 2 条并行，但覆盖里的 APM 列要共用同一套「在跑」定义；第 5 条不得和第 3 / 4 条抢最后几天。

与三域共背时间：W2 起和 Monitor / Log 对覆盖定义与 ID；W2～W3 和 APM 对半日接入路径。

## 6. 风险与建议砍法

| 风险 | 为什么会发生 | 十月怎么处理 |
|---|---|---|
| 把第 1 条做成重装安装器 | 失败类型多，容易顺手重构 `tasks/installer.py` | 只补验收面和人话；安装状态机不重写 |
| 覆盖表做成第二套 CMDB | 主机 × 模块很容易画成拓扑 | 只做一张表 + 缺失筛选 |
| log / apm 推送写假成功 | 对端 ingest 可能还没有 | 未就绪 = 可补推失败，验收写死 |
| 第 4 条滑向 K8s 注入 | 竞品故事好讲 | 文档和验收只写接入点 + 制品到达 |
| 第 5 条抢主保 | 可升级筛选看起来「就差一个按钮」 | 默认不排；按钮不等于任务 + 回滚 |
| 和三域抢探针安装 | 各域都想在自己页面装 Agent | 探针安装只进节点管理；三域十月仍是策略 |
| 做成远程执行 | 首次触达已经用了 Ansible Executor | 通道可以继续用；产品入口不暴露任意命令 |
| 老节点被新默认值带偏 | 推送默认勾选 log / apm | 存量不自动补推；只在新装或用户显式勾选时推 |

建议砍法，按顺序用：

1. 先砍第 5 条（默认就准备砍）。
2. 第 4 条若只剩下载：保「指到正确接入点 + 系统内下载 + 校验」，Sidecar 落盘移十一月。
3. 第 3 条若 APM 接收面未就绪：先交 log + 字段，apm 目标以「未就绪可补推」上线，不允许假成功。
4. 不砍第 1 条的「在跑 + 人话失败」，不砍第 2 条覆盖表。没有这两条，十月节点管理交不出信任。
5. 任何情况下都不把维护窗、远程执行平台、插件商店、K8s 注入、重做安装通道加进十月。

## 7. 明确不做（整月）

- 第二套 Ansible / Salt / TAT / 云助手远程执行平台；任意命令、剧本市场。
- SkyWalking 类语言 Agent K8s 注入、自动改 Deployment、RUM、公网 OTLP Token。
- 完整插件商店、动态 CMDB 拓扑策略引擎、按资产自动铺采集器。
- 维护窗、静默、级别抑制、降噪、升级值班——全部归告警中心。
- 重做自动 / 手动 / Token 安装通道。
- 三域策略计算、试跑、样本回跳（各走 #20 / #21 / #22）。
- 灰度发布编排、跨区域一键升级、与维护窗联动的升级日历。

十月结束时，对外可讲的仍是一句人话：探针装得上，状态看得见，三域接得上。批量升级能做就做，做不完不丢人。运营降噪继续在告警中心。

## 8. 给群聊的短结论

十月节点管理定稿 5 条，主保前 4 条：装完能验（在跑 + 心跳 + 人话失败）；覆盖一览看主机 × 采集器 × 三域缺什么；`push_targets` 从 cmdb/monitor 扩到 log、apm 并对齐实例 ID；APM 共背半日能指到区内接入点、探针能下到机器。第 5 条批量升级可砍，筛选已有。维护窗继续只进告警中心；探针安装不进三域十月清单。3 周保「装得上、看得见、接得上」。
