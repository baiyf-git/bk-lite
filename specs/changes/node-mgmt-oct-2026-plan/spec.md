# BK-Lite 节点管理 · 2026 年 10 月迭代规划

Status: ready for scheduling  
Audience: 产品 / 研发排期 / 三域共背  
Scope: 节点管理（`web/src/app/node-manager` + `server/apps/node_mgmt`）及与 Monitor / Log / APM 的身份与接入接缝  
Horizon: 国庆后约 3 周、约 1 组全栈；略满可砍，不再加项

一句话价值：机器纳管之后，监控 / 日志 / 调用链真的在采，坏了能看懂，三域认的是同一台机器。

本文是最终十月规划，可直接拆故事排期。不是审稿中间态，也不是实现规格。  
三域十月继续主保策略侧；**探针安装只在节点管理**，不进 Monitor / APM / Log 十月清单。

## 0. 可粘贴定稿

```
【节点管理：探针装得上、状态看得见、三域接得上】
	1，装完能验：采集器/配置是否在跑、最近心跳；失败原因说人话（必须交付）
	2，覆盖一览：主机 × 采集器 × 模块（Monitor / Log / APM），缺什么一眼看到（必须交付）
	3，push_targets 扩到 log、apm；节点↔CMDB↔三域实例 ID 对齐（必须交付）
	4，APM 接缝：云区域区内 OTLP + 多语言探针下载/下发；与 APM 共背验收——半日能指到正确接入点、探针能下到机器（必须交付）
	5，批量升级控制器/采集器（可升级筛选已有；补任务化升级+回滚摘要）（有余量再做，否则移十一月）
```

说明（规划纪律，不改主保）：

- 维护窗 / 静默 / 级别抑制归告警中心。
- 探针安装不进 Monitor / APM / Log 十月清单；三域继续主保策略侧。
- 节点管理主保 1 + 2 + 3 + 4；5 可砍。
- 与三域共背：1 / 2 / 3 对 Monitor + Log；4 对 APM。`push_targets` 现网仅 cmdb / monitor。

## 2. 证据分层

### 仓库事实

- 安装通道已在：`InstallerViewSet` 覆盖控制器安装 / 卸载 / 重试 / 手动安装、采集器安装、Windows / Linux 下载、安装命令。首次触达是 SSH、WinRM（云区域 Executor）或 Token / 手动，不是缺口。
- 心跳半套已在：Sidecar 回写 `Node.status` / `metrics` / `updated_at`；列表把 60 秒内上报标为活跃；采集器按心跳计数。见 `services/node.py`。
- 失败类型已在、人话没有：`FAILURE_SUMMARY_MAP` 能区分超时、连不上、鉴权、磁盘、架构、时钟偏差，文案是英文技术句。见 `utils/installer_schema.py`。
- 覆盖一览不存在：列表只看单台 Sidecar 和托管采集器数量。采集器标签已有 `monitor`、`apm`（预置 `OTel-Collector`）；Log 用 `node_ids` 下配置；节点侧没有「主机 × 模块」汇总。
- 推送真缺口：`ALLOWED_PUSH_TARGETS = ("cmdb", "monitor")`，前端 `ModulePushTarget` 同样只有这两项。`Node` 有 `cmdb_id` / `monitor_id` / `push_status`，**没有** `log_id` / `apm_id`。见 `services/module_push.py`、`models/sidecar.py`。
- 升级半套：`NodeComponentVersion.upgradeable` 和列表筛选已有；没有批量升级任务，没有回滚摘要。
- APM 地址已能生成：区内 OTLP/HTTP `:4318` 和五类语言探针系统内下载走 APM，不走节点管理包上传。节点管理还没有共背「指到 / 下到」验收。见 `docs/operations/apm-probe-artifact-release.md`。
- 新装延迟推送已有记忆，只对已存在节点立即推。不能写成「装完就自动和三域对齐」。

### 已确认产品决定

- 主题与主保见第 0 节，不扩大范围。
- 保持底座（Controller / Sidecar）+ 插件（采集器）。安装保留远程批量 + Token / 手动。
- 节点管理 ≠ 远程执行。云助手 / TAT / Ansible 只当首次触达通道。
- 策略化分组、灰度、K8s 语言探针注入后置。

### 当前假设

- 覆盖列按已售模块裁剪，与现网推送勾选纪律相同。
- 第 3 条复用现有 `module_push`（显式勾选、失败不阻断纳管、详情可补推），不新造同步总线。
- 第 4 条验收是「接入点正确 + 制品到达」，不是把语言 Agent 收成长期托管采集器。
- 第 1 条人话覆盖「安装失败」和「任务成功但没在跑」两类。

### 待确认（不挡排期）

- Log / APM 是否已有与 Monitor 同级的 ingest。节点侧先开目标、字段、补推；对端未就绪只记「未就绪」，不写成功。
- 覆盖表入口：节点列表加列，或云区域下一张页。十月只做一张表。
- 探针「下载命令」还是「Sidecar 落盘」。最低验收是目标机拿到制品。

## 3. 边界与伪需求

### 3.1 和谁分活

| 谁 | 十月做什么 | 不做什么 |
|---|---|---|
| 节点管理 | 装完能验；覆盖表；推到 log / apm 并对齐 ID；指到区内 OTLP、把探针下到机器 | 不算 P95 / 环比；不配日志或 APM 策略；不设维护窗 |
| Monitor | 策略相对计算 + 试跑。采集是否在跑、主机是否对齐，与节点管理共背 1 / 2 / 3 | 不在监控页做探针安装 |
| Log | 策略相对计算 + 试算 + 样本回跳。日志采集覆盖和实例 ID，与节点管理共背 1 / 2 / 3 | 不在日志十月清单做探针安装 |
| APM | 策略相对计算 + Trace 隔离。区内接入点和探针到达，与节点管理共背 4 | 不在 APM 十月清单做 K8s 注入 |
| 告警中心 | 维护窗、静默、级别抑制、降噪、升级 | 不看心跳，不算覆盖 |

对外一句：**节点管理负责装得上、看得见、ID 对得上；三域负责怎么判定；告警中心负责响不响。**

### 3.2 不要当十月新功能

- 第二套 Ansible / Salt / TAT / 云助手远程执行平台，或任意命令入口。
- SkyWalking 类语言 Agent 的 K8s 注入、改客户 Deployment。
- 完整插件商店、动态 CMDB 拓扑策略引擎、按资产自动铺采集器。
- 把抑制 / 维护窗做进节点管理。
- 重做自动 + 手动 + Token 安装通道。现有通道够用，缺的是能验 / 覆盖 / 接缝。

对照「装完能不能信、覆盖缺不缺、身份接不接得上」。云助手 / TAT / Ansible 只当首次触达，不对标成产品。

| 十月用得上的能力 | 我们现在 | 蓝鲸 NodeMan | Elastic Fleet | Datadog Fleet Automation | 华为 UniAgent | 十月 |
|---|---|---|---|---|---|---|
| 底座 + 插件 | 已有 | 有 | 有 | 有 | 有 | 保持 |
| 远程批量 + Token / 手动 | 已有 | 有 | 有 | 有 | 有 | 不重做 |
| 心跳 + 运行状态能信 | 半套，失败偏英文 | 插件状态是前提 | last check-in | Agent health | 心跳 + 插件 | **做第 1 条** |

## 5. 需求拆解

每条按同一结构写：背景 / 用户与场景 / 范围 / 方案要点 / 验收标准 / 优先级与可砍 / 依赖与共背方。

### 5.1 装完能验

**背景**  
自动 / 手动安装能把控制器装上去，进度页也能走到成功或失败。交付仍会问：采集器在不在跑？刚才为什么失败？现在要么看英文步骤，要么 SSH。任务成功但采集没上报，会被当成「已经好了」。

**用户与场景**

- 交付工程师刚装完一批 Linux / Windows 节点，要当场确认 Sidecar 有心跳、该装的采集器和配置在跑，才能交给监控 / 日志同事配策略。
- 安装失败时，现场要立刻知道是连不上、权限不够、磁盘不够、包架构不对、时钟差太多，还是装上了没回连，并知道下一步是重试、改凭据、查云区域，还是改手动。
- 值班看到某台「安装成功」但不出数，要能在节点管理核对最近心跳和采集器是否在跑，而不是先怀疑策略。

**范围**

- 做：安装结束（含手动回连）展示最近心跳时间、控制器是否心跳、本次相关采集器 / 配置是否在跑；高频失败用人话说明原因和下一步；任务成功但未上报不得标成采集正常。
- 不做：重写安装状态机；新开 SSH / 任意命令诊断台；把维护窗做进安装结果；重做自动 / 手动 / Token 通道。

**方案要点**  
复用 Sidecar 心跳、`Node.status.collectors`、`Installer` 任务结果、`FAILURE_SUMMARY_MAP`。在现有安装进度页和节点详情补三件事：最近心跳、是否在跑、人话原因。活跃窗口继续用现网 60 秒，文案写「最近心跳」，不要只丢绿灯。不新做状态机。

**验收标准（可测）**

1. 自动或手动安装结束后，同一任务能读到最近心跳时间；无心跳时不得显示采集正常。
2. 控制器回连成功、目标采集器未出现在心跳 `collectors` 或状态非运行：页面为「未在跑」，不得因任务成功写成已覆盖。
3. 连不上、鉴权失败、超时、时钟偏差、包架构不匹配：页面是中文人话 + 下一步，不直接展示英文 `error_type`。
4. 同一失败任务可重试或转手动，节点记录保留。
5. 页面和接口不出现任意命令入口；生产日志不含凭据、安装 Token、应答正文。

**优先级与可砍条件**  
P0，不可砍。人话可先覆盖上面 5 类高频失败，「未知」用「安装未完成，请看步骤或重试」兜底。不可把「在跑 + 心跳」降级成只改文案。

**依赖与共背方**  
依赖现有安装任务和心跳，不依赖告警中心。Monitor / Log 共背：本域采集器装完后，能在节点侧被看成在跑。APM 的 OTel 是否在跑，供第 2 / 4 条复用同一口径。

### 5.2 覆盖一览

**背景**  
交付要回答「这批机器监控齐了吗、日志齐了吗、APM 齐了吗」。现在只能一台一台点托管程序。缺 Vector 或没装 OTel，往往要到三域不出数才发现。

**用户与场景**

- 售前 / 交付按云区域对 50 台主机做验收，要一张表勾出谁缺 Monitor、谁缺 Log、谁缺 APM。
- 节点管理员筛「Log 缺失」后，从格子回到现有安装或详情，补装缺的采集器。
- 监控同事看到某台「已装 Telegraf 但心跳超时」，不应把它算进已覆盖。

**范围**

- 做：一张覆盖表。行是主机，列是已售模块（Monitor / Log / APM）及对应采集器。格子：已安装且在跑、已安装但未在跑 / 无心跳、未安装、不适用。能按「某模块缺失」筛。点格子回现有详情或安装入口。
- 不做：第二张大盘或拓扑图；按 CMDB 自动铺采集器；跨云区域全球地图；未售模块列和「缺失」误报。

**方案要点**  
在 `node_mgmt` 汇总节点、托管采集器、采集器标签（`monitor` / Vector·Beat / `apm` 的 OTel）和已关联三域实例。入口二选一：列表加列，或云区域下一张页。十月只做一张。在跑口径必须与第 1 条相同。

**验收标准（可测）**

1. 同一云区域、同一权限范围，能列出缺 Monitor 采集器、缺 Log 采集器、缺 APM（OTel 或语言探针入口）的主机。
2. 已装但超过活跃窗口无心跳的格子 ≠「已覆盖」。
3. 未购买 Log 或 APM 时，不出现该列，也不出现该模块缺失。
4. 覆盖表与节点详情托管程序一致：详情在跑，表上不得标缺失；详情未装，表上不得标已覆盖。
5. 从缺失格子能回到现有节点详情或安装入口，不出现第三套安装向导。

**优先级与可砍条件**  
P0，整张表不可砍。可砍的只是入口形态（加列或独立页，选成本低的）。不可改成「只在详情里看」。

**依赖与共背方**  
依赖第 1 条在跑 / 心跳口径。Monitor / Log 共背缺失定义（例如主机监控看 Telegraf，文件日志看 Vector / Filebeat）。APM 列与第 4 条共用 OTel / 探针入口定义。

### 5.3 `push_targets` 扩到 log、apm，并对齐实例 ID

**背景**  
节点已能勾选推到 CMDB、Monitor，并回填 `cmdb_id` / `monitor_id`。Log / APM 实例对不上同一台机器。三域十月各自做策略，拼数据仍会认成三台主机。代码白名单和前端类型都还只有 cmdb / monitor。

**用户与场景**

- 新装节点时，已购 Log / APM 的客户希望和 CMDB / Monitor 一样默认勾选推送，取消则不推。
- 详情里补推失败或未推送的 log / apm，成功后两边都能看到对方 ID。
- 运营分析按主机拼监控、日志、调用链时，三域实例能回到同一个 `node_id` / `cmdb_id`。

**范围**

- 做：白名单增加 `log`、`apm`；节点持久化与 `cmdb_id` / `monitor_id` 同级的关联 ID；`push_status` 按目标记录；创建 / 安装 / 详情补推交互与现网一致（已售默认勾、取消不推、失败不阻断纳管）；冲突拒绝静默合并；对端未就绪记可补推失败，不写假成功。
- 不做：存量自动补推；级联暗建未勾选目标；重做 CMDB 拉同步或第二条总线；把 Log / APM 业务事实反推回节点；改 CMDB `inst_uuid` 规则。

**方案要点**  
扩 `ALLOWED_PUSH_TARGETS` 和前端 `ModulePushTarget`；`Node` 补 log / apm 字段；`module_push` / `module_link` / `module_ingest` 按 Monitor 既有契约加两个目标。身份仍以节点 ID 优先，CMDB 仍用 `inst_uuid`。对端无接收面时状态为未就绪 / 失败，详情可再推。

**验收标准（可测）**

1. 安装或详情提交 `push_targets` 含 `log` / `apm` 时，白名单接受；未出现在勾选列表的目标，服务端不调用对端。
2. 推送成功：节点能读到对应实例 ID，对端能读到 `node_id`；再推一次不新建重复实例。
3. 只勾选 monitor 时，行为与改前一致；老节点无 log / apm ID 时显示「未推送」，不报错。
4. 对端未就绪或超时：节点仍在，状态为人话「未就绪 / 失败，可补推」，`push_status` 不得为成功。
5. 已售模块才默认勾选；用户取消后，创建成功且该目标无新实例。
6. 关联冲突（同一 ID 指向不同实体）拒绝合并，并留下可操作说明。

**优先级与可砍条件**  
P0。白名单、字段、补推入口不可砍。若 APM 接收面 W2 仍没有：log 先闭环，apm 以「未就绪可补推」上线，禁止假成功。不可改成让用户手填对端 ID。

**依赖与共背方**  
样板是现网 CMDB / Monitor ingest。Log / APM 共背接收、回填 `node_id`、冲突语义。Monitor 共背：扩目标后，只推 monitor 不回归。不依赖告警中心。

### 5.4 APM 接缝：区内 OTLP + 探针下发

**背景**  
APM 接入页已能按云区域给出区内 OTLP/HTTP 地址，也能拼出五类语言探针的系统内下载地址。现场卡在：指错区域、机器下不了包、节点管理不知道这台机器 APM 接不接得上。K8s 注入是另一条路，十月不做。

**用户与场景**

- 应用负责人选对云区域后，要在半天内得到正确区内接入点，并把 Java / Python / Node.js / Go / .NET 探针放到目标机（当前平台已声明的范围）。
- 节点管理员在覆盖表里看到某台 APM 未到达，要从节点管理指到同一接入点、同一下载口，而不是和 APM 页各写各的。
- 区域未配 `NODE_SERVER_URL` 或某语言包未发布时，要看到「区域未配 / 该语言包未发布」，不能装成网络故障。

**范围**

- 做：展示该云区域 / 该节点的 OTLP 接入点（与 APM 接入页一致，区内 `:4318`）；提供五类语言系统内下载 / 下发入口和结果（成功、下不到、区域未配、包未发布）；校验目标机拿到的制品（大小或哈希）；OTel Collector 纳入第 2 条 APM 列。
- 不做：K8s webhook / 自动注入；公网 OTLP Token；访问 GitHub / PyPI；把语言 Agent 登记成长期托管采集器（OTel Collector 除外）；RUM；把 `deploy/apm` 当生产真相源。

**方案要点**  
复用云区域 `proxy_address` / `NODE_SERVER_URL`、预置 `OTel-Collector`、APM `open_api/probe/download`。节点管理补「接入点 + 下载 / 下发」结果。最低交付是系统内下载 + 校验；经 Sidecar 落盘是加分，W2 仍重则降级。

**验收标准（可测）**

1. 同一云区域，节点管理给出的 OTLP 地址与 APM 接入页完全一致，且为区内 `:4318`，不是公网 Token 入口。
2. 已声明的五类语言能从系统内地址下载；缺制品时文案为「该语言包未发布」，不是「网络错误」。
3. 区域缺少 `NODE_SERVER_URL` 或代理地址时，明确「区域未配」，并阻断假装成功的下发。
4. 目标机文件能对上平台登记制品（大小或哈希）；失败可重试，不删节点。
5. 与 APM 共背走通半日路径：选区域 → 看到接入点 → 下载探针 → 机器上有文件。
6. 产品表面不出现 K8s 注入开关。

**优先级与可砍条件**  
P0。「指到正确接入点 + 系统内下载 + 校验」不可砍。可砍：经 Sidecar 落到指定目录（降级为下载命令 / 包 + 校验）。不可用半套注入或公网源顶上。

**依赖与共背方**  
APM 共背接入配置、探针制品发布和半日路径。第 2 条 APM 列共用 OTel / 探针到达定义。第 1 条提供 OTel 是否在跑。不依赖告警中心，不依赖第 5 条。

---

### 5.5 批量升级控制器 / 采集器（可砍）

**背景**  
列表能筛「可升级」，版本旁也有提示。真要升一批，还是重新走安装，没有任务摘要，也没有回滚摘要。这是成熟度，不是十月信任闭环。

**用户与场景**

- 管理员筛出 20 台可升级控制器，希望发一条任务看每台成功 / 失败，而不是逐台重装。
- 升级后部分失败，需要知道谁还能回到升级前版本，谁要手工处理。

**范围**

- 做（仅有余量）：对已标可升级的控制器 / 采集器发升级任务；节点级进度；结束给成功 / 失败数和回滚摘要（谁回得去、升级前版本、谁要手工）。
- 不做：灰度百分比；分批日历；与告警中心维护窗联动；跨云区域一键全球升级；把未标可升级的节点混进任务。

**方案要点**  
复用 `NodeComponentVersion`、`PackageVersion`、安装 / 动作任务。不新写作业引擎。回滚只针对本次任务写过的节点。人话失败复用第 1 条。

**验收标准（可测，仅真做时算）**

1. 可升级筛选结果能进入升级任务；操作系统或架构不一致的批次提交被拒绝。
2. 任务能列出每台成功 / 失败和人话原因。
3. 回滚摘要列出可回滚节点和升级前版本；回滚失败不删节点。
4. 未标可升级的节点不能被选进任务。

**优先级与可砍条件**  
P1。W3 才看；1～4 任一未验收则整条移十一月。禁止只加一个「升级」按钮却没有任务和回滚摘要。

**依赖与共背方**  
依赖第 1 条人话失败和现有包版本。与三域策略、告警中心无关。不阻塞 1～4。

## 6. 排期（3 周，1 组全栈）

| 周次 | 交付 | 砍闸 |
|---|---|---|
| W1 | 第 1 条：心跳 / 在跑进入安装结束态，高频失败人话上进度页。第 3 条：白名单 + 字段扩 log / apm，补推形态与现网相同 | 不动第 5 条；对端未就绪不写成功 |
| W2 | 第 2 条覆盖表；第 3 条与 Monitor / Log 对 ID；第 4 条接入点 + 探针下载入口 | 覆盖只做一张表；探针落盘若重，先保下载 + 校验 |
| W3 | 1～4 打磨与共背验收；半日 APM 路径走通；有余量再开工第 5 条 | 第 5 条未开工则移十一月 |

并行：第 2 条依赖第 1 条口径；第 4 条可与第 2 条并行，APM 列必须共用「在跑」；第 5 条不得抢第 3 / 4 条最后几天。  
共背：W2 起对 Monitor / Log 的覆盖定义与 ID；W2～W3 对 APM 半日路径。

建议砍法（按顺序）：

1. 先砍第 5 条。
2. 第 4 条只保接入点 + 系统内下载 + 校验。
3. 第 3 条 APM 接收面未就绪时，apm 以未就绪上线，先闭环 log。
4. 不砍第 1 条「在跑 + 人话失败」，不砍第 2 条覆盖表。
5. 不把维护窗、远程执行、商店、K8s 注入、重做安装加进来。

## 7. 给群聊的短结论

十月节点管理就这一份规划。主保 4 条：装完能验（在跑 + 心跳 + 人话失败）；覆盖一览看主机 × 采集器 × 三域缺什么；`push_targets` 从 cmdb/monitor 扩到 log、apm 并对齐实例 ID；APM 共背半日能指到区内接入点、探针能下到机器。第 5 条批量升级可砍，筛选已有。维护窗只进告警中心；探针安装不进三域十月清单。3 周保「装得上、看得见、接得上」。
