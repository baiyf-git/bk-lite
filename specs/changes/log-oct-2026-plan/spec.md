# BK-Lite Log 十月迭代规划

Status: ready  
Audience: 产品 / 研发排期  
Scope: 仅 BK-Lite Log（`web/src/app/log` + `server/apps/log`，VictoriaLogs）  
Horizon: 国庆后约 3 周，约 1 组全栈；略满可砍，不再加项

本文是 **仓库内唯一一份** Log 十月规划。#18 的 `calc_mode` 写法收进附录 A，只服务第 1 / 2 条怎么配；读者不要据此以为十月只做计算方式。#22 是本稿前身，口径以本文为准。

一句话：**策略能配相对计算，配完能试算，告警能带样本回跳。**

---

## 1. 背景与问题

值班和策略配置人现在只能配两件事：窗口里有没有关键字，或窗口里的 count / sum / avg / max / min 过没过一条固定线。业务流量一涨，绝对条数策略就误报；流量一跌，又容易漏报。配完要等下一个扫描周期才知道对不对。手机上的告警只有一句话，点进去还停在告警列表，聚合告警甚至可能把 `stats` 拼进检索框，值班人看不到「当时那批日志」。

这不是「没有日志告警」。现网已经能扫、能落域内告警、能通知、能从详情跳检索。缺口是三段闭环没接上：

1. 策略说不出「变快了 / 比上一窗高了」。
2. 配完不能当场验「这一窗会不会响」。
3. 响了之后通知里没有样本，回跳也不干净。

对外对比只对「日志策略怎么判定、配完能不能验、响了能不能回到日志」，不对 ELK / Datadog 全家桶。竞品桌面上的常用能力是 rate、等长窗变化、占比、试运行、通知带上下文；抑制 / 维护窗 / 降噪他们也有，但在 BK-Lite 里已经归告警中心。

### 1.1 仓库事实

- 策略只有 `keyword`（命中即告）和 `aggregate`（本窗 `count` / `sum` / `avg` / `max` / `min` 对阈值）。表单与扫描都没有 `calc_mode`，没有对照窗，没有占比。
- 扫描在 `server/apps/log/tasks/services/policy_scan.py`：单窗 LogsQL `stats` 后比阈值。关键字会取样本，默认 `limit=5`（`_get_keyword_sample_limit`）；聚合只存 `aggregate_result` / `query_result`，不存原始日志。
- 策略页已有查询联想（`specs/changes/log-policy-query-autocomplete`），当时明确不做服务端试运行。现有 `logPreview.tsx` 只预览近期命中日志，不算「会不会触发」。
- 告警详情已能打开检索：`/log/search?query=&startTime=&endTime=&log_groups=`。聚合详情会把 `stats` 拼进查询（`web/src/app/log/(pages)/event/alert/information.tsx` 的 `buildVictoriaLogsQuery`）。
- IM / 邮件通知只有时间、告警内容、策略名，以及指向 `/log/event/alert` 列表的链接（`_format_notice_content`）；不带样本，也不预填检索。
- 检索页已有组织级「保存 / 加载条件」：`SearchCondition`（名称 + query + 日志分组 + 时间，相对时间靠 `origin_value`）。产品决策已写明：它是命名查询，不是用户习惯表。
- 日志告警没有自动恢复。抑制、维护窗、相关性降噪、事故聚合在告警中心。
- 节点侧：`CollectInstance.node_id` 已有字段；节点管理 `push_targets` 现网只认 `cmdb` / `monitor`，覆盖一览不含 Log。这些由节点管理十月规划共背，**不进本文功能清单**。

### 1.2 已确认产品决定

- 主保：1 速率 / 变化量 + 3 试算预览 + 4 样本回跳。
- 2 错误占比可砍：仅 count；总量为 0 不触发。
- 5 保存查询默认不排：组织级现网已有；个人星标仅 W3 余力。
- 抑制 / 维护窗 / 降噪归告警中心。探针安装归节点管理。
- 对外对比口径是「Log 判定 + 告警中心运营」，不是「Log 做成第二套告警中心」。
- 三域共用：缺对照不误报、试跑不落告警。Log 速率 = 本窗 `count / period`；变化量 = 上一等长窗。不做 Monitor / APM 的 1h / 1d 环比档。
- 十月不发明日志自动恢复。命中则持续活跃，人工关闭。

### 1.3 当前假设

- 「错误」由策略里一条错误侧查询表达（级别、状态码、关键字等），平台不内置错误分类器。
- 试算看「现在这套条件套在最近一个完整窗上会怎样」，不是回放历史每一次扫描。
- 告警中心副本继续收结构化生命周期事件；样本正文只保证 Log 详情和 Log 自己发出的 IM / 邮件可读。

## 2. 目标与非目标

### 2.1 目标

交付后，配置人能用表单表达「单位时间更快了 / 比上一窗变了」，当场看到本窗、对照或总量、变换后值和会不会触发；值班人从通知或详情能看到最多 10 条样本，一跳回到当时的查询、日志分组和触发窗。

存量无 `calc_mode` 的 keyword / aggregate 行为不变。用户不写 PromQL、Zabbix 或第二条 LogsQL。

### 2.2 非目标（整月）

| 边界 | 谁做 / 为什么不做 |
|---|---|
| 抑制、静默、维护窗、屏蔽、智能降噪、升级、值班表 | 告警中心。Log 验收不写「维护期不响」 |
| 探针安装、装完能验、覆盖一览含 Log、`push_targets` 扩到 log、节点 ↔ 日志实例 ID 对齐 | 节点管理十月规划共背。Log 只配合契约与验收，不把这些写成 Log 交付项 |
| 日志告警自动恢复、转派、告警中心处理人回写 | 领域决策已后置 |
| 同比、周同比、工作日基线、1h / 1d 环比档、异常检测、预测、百分位、cardinality | 成熟度增强；且与 Monitor / APM 的环比档刻意错开 |
| 手写两条 LogsQL、通用规则引擎、查询语法校验器 | 3 周表单闭环，不是表达式产品 |
| 日志大盘、组织共享查询中心、把命名查询改成用户习惯 | 第 5 条都默认不排，更不扩 |
| 重做 S3 快照、通知模板编辑器、告警中心富文本 | 第 4 条是补证据，不是新存储产品 |
| 前端自己算速率 / 变化量 / 占比 | 试算必须走扫描引擎 |

### 2.3 与告警中心

| 谁 | 做什么 | 不做什么 |
|---|---|---|
| Log | 用本窗 / 对照窗 / 总量判定该不该响；试算同一套数；把 ≤10 条样本和回跳条件留给值班人 | 不抑制、不设维护窗、不相关收敛 |
| 告警中心 | 收日志告警副本后做屏蔽、维护窗、分派、升级、事故、降噪 | 不代替 Log 算速率 / 占比，不改 Log 的触发事实 |

对外只说一句：**Log 负责判定和证据，告警中心负责运营。**  
试算只回答「按当前条件，这一窗会不会触发」，不管告警中心后来是否屏蔽通知。

### 2.4 与节点管理

节点管理十月主保「装得上、看得见、接得上」：装完能验、覆盖一览含 Log、`push_targets` 扩到 `log`、节点 ↔ 日志实例 ID 对齐。这些写在第 3 节总表之外、第 4 条各需求的「依赖」和第 7 节协作里。

Log 十月功能清单 **不出现** 安装、覆盖、下发、实例对齐。没有节点侧能力，相对计算和样本回跳仍按已接入的日志数据验收。

### 2.5 三域同词不同引擎

| 词 | Monitor / APM | Log（本文） |
|---|---|---|
| 速率 `rate` | 指标序列上的 rate | 本窗 `count / period`（秒） |
| 变化量 `change` | 上一窗 Δ | 上一等长检测窗 Δ |
| 环比 `mom` | 对照 1h / 1d | **十月不做** |
| 试跑 / 试算 | 复用扫描引擎，不落告警 | 同左 |
| 缺对照 | 不误报 | 同左 |

## 4. 逐条需求拆解

### 4.1 速率 / 变化量（P0，必须交付）

**背景**  
聚合策略只能拿本窗一个绝对数字比阈值。流量涨时「5 分钟 300 条」和「5 分钟 30 条」对业务的含义完全不同，配置人却只能把阈值写成死数。竞品用表单就能配 rate 和等长窗变化；我们扫描侧已经会 `stats`，缺的是聚合之后、比阈值之前的变换。

**用户价值**  
流量正常爬升时不再只因为条数变多就响；要看单位时间速率，或是不是比上一窗真的变了。

**范围**

| 做 | 不做 |
|---|---|
| 聚合策略增加计算方式：绝对值（缺省）/ 速率 / 变化量 | 关键字策略做速率或变化量 |
| 速率 = 本窗命中 `count / period` 秒数（与 rule 里选了哪个聚合函数无关） | 把 sum / avg / max / min 的结果再除以 period 叫「速率」 |
| 变化量 = 本窗聚合值 − 上一等长窗同一聚合值 | Monitor / APM 的 1h / 1d 环比档、同比、工作日基线 |
| 对照窗写不出、查询失败或没有数据 → 本轮不触发、不通知 | 把缺失对照当成 0 去减，造成误报 |
| 分组策略按组对齐对照窗；对不上的组按「缺对照」 | 用户手写第二条 LogsQL 或 offset |
| 未选计算方式的老策略继续按本窗绝对值比阈值 | 新的 `alert_type`；抑制次数当成计算方式 |

**现状依据**

- 类型与条件：`server/apps/log/constants/alert_policy.py`（`TYPE_KEYWORD` / `TYPE_AGGREGATE`）、`server/apps/log/models/policy.py` 的 `alert_condition` / `period` / `schedule`
- 扫描：`policy_scan.py` 的 `aggregate_alert_detection`、`_build_aggregation_query`、`_check_rule_conditions`；窗口由 `_get_scan_window` + `period_to_seconds` + `INGEST_DELAY_SECONDS` 决定，只扫一窗
- 表单：`web/src/app/log/(pages)/event/strategy/detail/alertConditionsForm.tsx`、`conditionSelector.tsx`、`policyFormUtils.ts`；聚合函数枚举在 `web/src/app/log/constants/index.ts` 的 `FUNCTION_LIST`

**方案要点**

- 计算方式是 `alert_condition` 上的字段（建议键名 `calc_mode`：`absolute` / `rate` / `change`），不是第三种 `alert_type`。
- 在现有「query + log_groups → stats → 比阈值」链路上，于 stats 之后插入变换；预览与扫描共用同一函数。
- 对照窗 = 本窗整体向前平移一个 `period`，两边都扣摄入延迟。用户看不到 offset。
- 阈值量纲随模式切换：条数、条 / 秒、Δ。
- 非法组合（例如 keyword 选 `rate`）在保存期拒绝，不拖到扫描失败。

**验收标准**

- 策略表单能选「绝对值 / 速率 / 变化量」；老策略打开仍是绝对值，保存后扫描结果与现在一致。
- 速率：同一查询在 5 分钟窗里 300 条，变换后值为 1 条 / 秒；阈值按变换后的值比。
- 变化量：本窗 120、上一窗 80，变换后值为 40；上一窗查询失败、无数据或窗口尚未形成，本轮不建告警、不发通知。
- 分组策略按组对齐对照窗；对不上的组按「缺对照」处理。
- 用户不能手写第二条 LogsQL 来表示对照窗。
- 缺省 `calc_mode` 不得变成速率。兼容用例是发布门禁。

**依赖**

- 只依赖 VictoriaLogs 双窗查询和现有 `period`。不依赖告警中心，也不依赖节点管理十月项。
- 告警中心继续收触发后的副本；不负责算 Δ。

**风险**

- 双窗拖慢扫描：对照失败 = 不触发，不重试到误报；超时记失败原因，不回退成绝对阈值。
- 老策略被新默认值带偏：缺省必须是现在的绝对值。
- 和 Monitor 「环比」文案撞车：对外用「变化量（较上一窗）」，不用「环比」。

### 4.2 错误占比（P1，可砍）

**背景**  
错误条数往往跟着流量涨。只配「ERROR > 100」会在大促时误报，在低峰时漏报。占比是第 1 条引擎上的第三个 `calc_mode`，不是另一条产品。

**用户价值**  
值班看的是「错得是不是更密了」，不是「今天请求更多了」。

**范围**

| 做 | 不做 |
|---|---|
| `calc_mode = ratio`；配置人填一条错误侧查询 | 手写两条 LogsQL |
| 总量 = 同一日志分组、同一窗口、去掉错误过滤后的 `count` | 对 sum / avg / max / min 做占比 |
| 占比 = 错误 count ÷ 总量；总量为 0 不触发 | 平台内置错误分类器、多条错误查询 |
| 与第 1 条共用扫描变换 | 把占比开放给关键字策略 |

**现状依据**

- 与第 1 条同一扫描入口；现网没有第二次查询，也没有比值。
- 查询条件已是策略表单一等字段（`alert_condition.query` + `LogQueryInput`）。错误侧复用它，总量由引擎去掉该过滤，而不是再给一个编辑器。

**方案要点**

- 表单形态：「错误查询 + 计算方式 = 占比」，阈值按 %。
- 总量查询由后端从错误查询推导，保存期校验推得出总量；推不出则拒绝保存。
- 与第 1 条同一变换函数；老策略不受影响。
- W2 末引擎或试算仍不稳，整条不做，不改成「先让用户填两条查询」。

**验收标准**

- 表单没有第二个 LogsQL 编辑器。
- 错误 20、总量 200，变换后值为 10%；总量 0，试算和扫描都是「不触发」，并写明原因是总量为 0。
- 与第 1 条共用扫描变换；老策略不受影响。

**依赖**

- 第 1 条的 `calc_mode` 与扫描变换先落地。不依赖告警中心，告警中心不负责算占比。

**风险**

- 双查询再打一次 VictoriaLogs：这是可砍的理由，不是改成双编辑器的理由。
- 错误查询过宽导致总量推导失败：保存期拒绝，并给可理解的校验文案。

### 4.3 策略条件试算预览（P0，必须交付）

**背景**  
相对计算配错的代价是静默误报或漏报。策略页今天只有日志命中预览和字段联想，当时规格写明「不做服务端试运行」。没有试算，第 1 条在真实环境不可交付。

**用户价值**  
配完立刻知道「按现在的数据，这一窗会不会响」，不用把半成品策略开到生产上等下一个周期。

**范围**

| 做 | 不做 |
|---|---|
| 策略页试算：本窗值、对照值或总量、变换后值、是否触发、不触发原因 | 历史回放时间轴、查询语法校验器 |
| 预览 API 走扫描同一套取数、对照窗、变换和阈值判断 | 前端用本窗数字自己算 rate / Δ / 占比 |
| 只读：不写 Event / Alert / 快照，不发通知，不推告警中心 | 一次试算写入告警 |
| 缺对照 / 总量为 0 / 未过阈值 / 查询失败要说人话 | 按告警中心屏蔽规则预演「会不会通知」 |

**现状依据**

- 明确非目标：`specs/changes/log-policy-query-autocomplete/spec.md`「不新增……服务端保存前试运行」
- 现有预览：`web/src/app/log/(pages)/event/strategy/detail/logPreview.tsx` 只拉近期原始日志
- 扫描判定：`policy_scan.py` 的 keyword / aggregate 检测；尚无只读入口

**方案要点**

- 新增只读预览 API（或现有 Policy ViewSet 上的 action），内部调用与扫描相同的窗口计算和变换函数，禁止走 `create Event / Alert / notice()`。
- 时间窗与线上扫描对齐（含 `INGEST_DELAY_SECONDS`），避免「试算过了、下一轮扫不过」。
- 无日志分组或查询为空时，试算不可用，但不挡保存绝对值老策略。
- 试算失败只留在策略页，不产生告警噪声。

**验收标准**

- 同一草稿条件，试算「是否触发」与下一次真实扫描在同一时间窗上的结论一致。
- 缺对照、总量为 0、查询失败时，试算明确说「不触发 + 原因」，不会显示成触发。
- 前端不得用本窗数字自己算速率 / 变化量 / 占比来决定是否触发。
- 无日志分组或查询为空时，试算不可用，但不挡保存绝对值老策略。
- 试算失败只留在策略页，不产生告警噪声；不落 Event / Alert，不发通知，不进告警中心。

**依赖**

- 第 1 条（以及若未砍的第 2 条）的变换逻辑先可复用。
- 与告警中心无功能依赖；试算结果不考虑屏蔽 / 维护窗。
- 不依赖节点管理。

**风险**

- 试算和线上扫描各写一套：验收写死「同一函数」；发现双实现就停占比，先收口。
- 为做占比挤掉试算：不允许。第 3 条是主保，第 2 条可砍。

### 4.4 告警通知与详情附样本 + 一跳回检索（P0，必须交付）

**背景**  
关键字已经把样本写进 `EventRawData` / 快照，默认 5 条；聚合没有原始日志。通知只有一句话加告警列表链接。详情回跳对聚合会带上 `stats`，值班人落到的不是「当时那批日志」。缺口是补齐，不是重做快照体系。

**用户价值**  
手机上看告警就能看见当时几条日志，点一下回到检索，而不是先打开告警列表再猜时间窗。

**范围**

| 做 | 不做 |
|---|---|
| 触发快照统一最多 10 条样本 | 重做 S3 / MinIO 快照存储 |
| 关键字沿用现有样本链，默认上限从 5 提到 10 | 通知模板编辑器、告警中心卡片改版 |
| 聚合在同一过滤查询和触发窗内补取最多 10 条原始日志 | 回跳查询带上扫描用的 `stats` |
| Log 自己的 IM / 邮件展示样本摘要；渠道截断时至少留条数和回跳 | 把完整 payload / 凭据打进生产日志或通知 |
| 通知和详情回跳打开检索，预填：策略查询、日志分组、触发窗口 | 在 Log 里做屏蔽或自动恢复 |
| 样本取失败不阻断告警创建和通知 | 告警中心页面必须展示样本（非本条验收） |

**现状依据**

- 关键字样本：`policy_scan.py` `_get_keyword_sample_limit`（默认 5）、`keyword_alert_detection` / `_fetch_group_sample`
- 聚合 raw_data：同文件 `aggregate_alert_detection` 只写 `aggregate_result` / `rule` / `query_result`
- 存储：`EventRawData` / `AlertSnapshot`（`server/apps/log/models/policy.py`，S3JSONField）
- 通知：`_format_notice_content` 链到 `/log/event/alert`，无样本、无检索深链
- 回跳：`information.tsx` `checkDetail`；聚合走 `buildVictoriaLogsQuery()` 拼接 `stats`
- 检索已认：`/log/search?query=&startTime=&endTime=&log_groups=`（`web/src/app/log/(pages)/search/page.tsx`）

**方案要点**

- 复用关键字样本链，把默认上限改为 10；聚合在触发成立后再用**过滤查询**（不要 `stats`）补取。
- 回跳 query = 策略里的过滤条件，不是扫描语句。时间窗 = 触发窗（活跃告警的结束时间按现网详情语义，但链接必须能复现触发窗）。
- 通知正文：样本摘要 + 条数 + 检索深链。IM 字数不够就截断正文，不丢链接。
- 告警中心副本协议不因样本变长而改语义；屏蔽后通知被压住是告警中心行为，Log 仍保存样本。

**验收标准**

- 关键字和聚合触发后，详情都能看到 ≤10 条样本；没有样本时说明「本窗无原始日志」而不是空白。
- IM / 邮件能看到样本摘要，并有一条打开检索的链接；点开后查询、分组、起止时间与触发窗一致。
- 回跳查询是策略里的过滤条件，不包含扫描用的 `stats`。
- 样本取失败不阻断告警创建和通知；通知仍有回跳。
- 不把完整 payload、凭据或无界原文打进生产日志。

**依赖**

- 现有 `EventRawData`、检索 URL、系统管理通知渠道。
- 告警中心：副本协议不改语义；告警中心带不带样本不是本条验收。
- 不依赖节点管理十月项。

**风险**

- 把本条做成新快照产品：只补取样本和改通知 / 回跳。
- 渠道截断：正文截断仍保留条数和回跳。
- W3 只剩一天：只做通知回跳 + 关键字样本到 10 条；聚合样本可滑下一迭代。不可砍回跳。

### 4.5 保存查询（P2，默认不排）

**背景**  
检索页已经能按组织保存 / 加载命名条件。再做「保存查询」当新模块，是和现网抢同一入口。缺的只是「只属于我」以及列一起存——这是产品分叉，不是从零补能力。

**用户价值**  
个人常用检索能一键回到「查询 + 相对时间 + 列」。现网已经能保存组织级条件。

**范围**

| 做（仅 W3 余力） | 不做 |
|---|---|
| 在现有 `SearchCondition` 上加「仅自己可见」 | 新建第二套星标查询对象或菜单 |
| 允许把当前展示列写进 `condition` | 组织共享改造、查询市场、日志大盘 |
| 入口仍是检索页星标 / 加载 | 把命名查询迁进用户习惯表 |

**现状依据**

- 模型：`server/apps/log/models/log_group.py` `SearchCondition`（`name` + `condition` JSON + `organization`）
- API：`server/apps/log/views/search.py` `SearchConditionViewSet`，按组织过滤
- 前端：`web/src/app/log/(pages)/search/page.tsx` 保存时写入 `query` / `log_groups` / `time_range.origin_value`
- 决策：`docs/design/product-decisions/app-user-habits.md`——`SearchCondition` 是命名查询，不是习惯表

**方案要点**

- 默认整条不排。真做时只加可见性 + 列，不改入口。
- 组织级旧数据仍按现网可见，不做一次迁移成「仅自己可见」。

**验收标准（只有真做时才算）**

- 个人条件只有创建人在当前组织能加载；组织级旧数据仍按现网可见。
- 加载后恢复查询、日志分组、相对时间、展示列。
- 不出现第二套「星标查询」模型或菜单。

**依赖**  
现成 `SearchCondition`。与告警中心、节点管理无关。

**风险**  
被当成十月主功能。主保或占比吃紧时直接砍，不做到「只改文案」。

## 5. 三周排期与砍法

约 1 组全栈。能做完的是「一条计算引擎 + 一张策略表单 + 一个只读试算 + 通知 / 详情补证据」。

| 周次 | 交付 | 砍闸 |
|---|---|---|
| W1 | `calc_mode`：绝对值兼容、速率、变化量；扫描双窗；缺对照不触发；策略表单能选 | 不做同比、不做 1h / 1d 环比、不做占比 |
| W2 | 试算 API + 策略页预览；若 W1 稳定，接 count 占比 | 试算与扫描结论不一致则停占比，先修引擎 |
| W3 | 样本上限 10、聚合补样本、IM / 详情展示、回跳预填查询 / 分组 / 触发窗 | 个人星标只在 1+3+4 已验收时碰；否则不开工 |

并行约束：第 3 条不能等第 4 条；第 2 条不能先于第 1 条；第 5 条不能和第 4 条抢最后几天。

**砍法（按顺序用，不要同时砍主保的两头）**

1. 先砍第 5 条（默认就不做）。
2. 再砍第 2 条整条（不要改成手写双查询）。
3. 第 4 条若只剩一天：只做通知回跳 + 关键字样本展示到 10 条；聚合样本和下个迭代。
4. 不砍第 1 条的「缺对照不误报」，不砍第 3 条。没有这两条，相对计算不能上生产。
5. 任何情况下都不把抑制、维护窗、降噪、自动恢复、异常检测、大盘、探针安装加进十月。

## 7. 依赖与协作（非 Log 十月交付项）

### 7.1 告警中心

Log 触发后的副本、屏蔽、维护窗、分派、升级、事故、降噪继续走告警中心现网契约。十月不改副本语义来塞样本。屏蔽后通知被压住，Log 仍保存样本和回跳条件。

### 7.2 节点管理（共背，不进第 3 节清单）

下列项写在节点管理十月规划，由两边共背验收，**不是 Log 十月功能**：

产品语言对齐 `calc_mode` 与「试跑不落单 / 缺对照不误报」。引擎不复用：Log 作用在 LogsQL 窗口计数结果上，不接 MetricsQL。Log 不做 1h / 1d 环比档。

## 附录 A：`calc_mode` 写法（吸收 #18，仅服务第 1 / 2 条）

本附录说明「计算方式在现网链路上怎么加」，不是十月范围说明书。#18 原文里的 P1 短环比 `mom`、数值字段一等入口、`nodata`、P2 百分位 / 同比 / ML / cardinality、自动恢复 / 连续触发，**一律不进十月**。

### A.1 放在哪

只动策略详情的 **告警条件**。基本信息、通知配置不因计算方式改版（第 4 条改的是通知**内容**，不是通知表单）。

| 层 | 路径 | 十月做什么 |
|---|---|---|
| 策略页 · 告警条件 | `web/src/app/log/(pages)/event/strategy/detail/alertConditionsForm.tsx`、`conditionSelector.tsx`、`policyFormUtils.ts` | 增加 `calc_mode` 选择器；切换阈值单位文案。不新增第三种 `alert_type` |
| 策略页 · 试算 | 现有 `logPreview.tsx` 仍只预览日志；试算是新的只读结果区 | 展示本窗 / 对照或总量 / 变换后值 / 是否触发 |
| 扫描 | `server/apps/log/tasks/services/policy_scan.py` | 在 `stats` 之后按 `calc_mode` 取对照窗或比值，再比阈值；试算与扫描共用同一编译 |
| 落库 | `Policy.alert_condition` JSON；保存走现有 Policy serializer | `calc_mode` 及模式字段随策略保存，编辑能回填；缺省兼容现网 |
| 常量 | `server/apps/log/constants/alert_policy.py` | `TYPE_KEYWORD` / `TYPE_AGGREGATE` 保持；计算方式是条件字段 |

不改：告警中心、LogsQL 引擎、采集 / 提取器、节点安装。

### A.2 十月枚举

与 Monitor 产品语言对齐的名字，比较对象是 LogsQL 窗口聚合结果。

| calc_mode | 用户怎么配 | 变换 | 缺数据 |
|---|---|---|---|
| （缺省）keyword | 查询 + 分组 + 周期；有匹配就告 | 无 | 无命中即不告，与现网一致 |
| `absolute` | 现网聚合：count / sum / avg / max / min 比固定阈值 | 无 | 与现网一致 |
| `rate` | 计算方式 = 速率 | 本窗命中 `count / period_seconds`（不用 sum/avg 结果做速率） | 本窗 count 查失败则本轮不触发 |
| `change` | 计算方式 = 变化量 | 本窗聚合值 − 上一等长窗 | 对照缺失 / 失败 → 不触发 |
| `ratio`（可砍） | 计算方式 = 占比；错误侧用查询过滤 | 错误 count ÷ 同窗总量 count | 总量为 0 → 不触发 |

用户选枚举，不手写 `offset` 或第二条 LogsQL。`period` / `schedule` 继续只负责「窗口多长、多久扫一次」。

### A.3 明确不从 #18 带进十月

- `mom`（1h / 1d 或「短环比」作为独立档）
- `nodata` / 断流
- 数值字段一等入口重构
- `percentile` / `yoy` / `anomaly` / `cardinality`
- 自动恢复、连续触发

字段落库（需求级）：`calc_mode` 写入 `alert_condition`（或并列 JSON）。独立列不是必须。须随策略保存，编辑能回填。
